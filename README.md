# HighloadHW1 — мониторинг ручек микросервиса в Grafana

Домашняя работа №1 (ИТМО, осень 2026), трек Фуллстек.

Нохрин Арсений Николаевич

Pet-project из четырёх частей:

1. **items-service** — CRUD-микросервис на FastAPI с in-memory хранилищем, который отдаёт метрики Prometheus (latency, traffic, errors).
2. **Prometheus + Grafana** — сбор метрик с двух экземпляров сервиса («два датацентра»).
3. **Генератор дашборда** — CLI-скрипт, который в рантайме получает список ручек от сервиса и создаёт дашборд в Grafana через HTTP API.
4. **Нагрузка** — сценарий k6, который плавно выводит стек на фоновые ~30 RPS с небольшой долей ошибок 404 и 500.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

Через 3 минуты нагрузка выходит на плато, и на дашборде видны данные:

**http://localhost:3000/d/items-service** (логин и пароль — из `.env`)

> Сразу после старта панели пустые: метрики ручек появляются после первых запросов, а нагрузка стартует только после генератора дашборда и разгоняется постепенно.

Остановить и удалить контейнеры: `docker compose down`. Данные не сохраняются между запусками (volume не используются), каждый `up` поднимает стек с нуля.

## Порты

| Порт на хосте | Сервис | Что там |
|---|---|---|
| 8001 | app1 (`POD_ID=1`, `DATACENTER=dc1`) | API сервиса, `/metrics`, `/handlers` |
| 8002 | app2 (`POD_ID=2`, `DATACENTER=dc2`) | то же для второго экземпляра |
| 9090 | Prometheus | UI, список таргетов: `/targets` |
| 3000 | Grafana | дашборд |

Внутри сети compose сервисы обращаются друг к другу по именам: `app1:8000`, `app2:8000`, `prometheus:9090`, `grafana:3000`.

## Архитектура и порядок запуска

```
 ┌─────────┐   PromQL    ┌────────────┐  scrape /metrics (5s)  ┌────────────┐
 │ Grafana │ ──────────► │ Prometheus │ ─────────────────────► │ app1, app2 │
 └─────────┘             └────────────┘                        └────────────┘
      ▲                                                          ▲        ▲
      │ POST /api/dashboards/db                    GET /handlers │        │ HTTP-нагрузка
      │                                                          │        │
 ┌─────────────────────┐ ────────────────────────────────────────┘    ┌────────┐
 │ dashboard-generator │                                              │  load  │
 └─────────────────────┘                                              │  (k6)  │
                                                                      └────────┘
```

Порядок задаётся через `depends_on`:

1. `app1`, `app2`, `prometheus` стартуют первыми; Grafana ждёт, пока Prometheus станет healthy.
2. `dashboard-generator` ждёт, пока `app1`, `app2` и `grafana` пройдут healthcheck (`service_healthy`), создаёт дашборд и завершается с кодом 0.
3. `load` стартует после успешного завершения генератора (`service_completed_successfully`) и работает до остановки стека.

## Сервис

| Ручка | Описание |
|---|---|
| `POST /items` | создать запись → `201` |
| `GET /items/{item_id}` | получить запись → `200` / `404` |
| `PUT /items/{item_id}` | обновить запись → `200` / `404` |
| `GET /health` | служебная, `200` когда сервис готов |
| `GET /metrics` | служебная, метрики в формате Prometheus |
| `GET /handlers` | служебная, список бизнес-ручек для генератора |

Хранилище — словарь в памяти процесса. Uvicorn запущен с одним воркером: при нескольких воркерах у каждого было бы своё хранилище и свои метрики.

**Искусственные ошибки.** Переменная окружения `FAIL_RATE` (в compose `0.03`) задаёт шанс, с которым бизнес-ручка отвечает `500`. Сбой подключён как FastAPI-зависимость только к бизнес-ручкам.

## Метрики

Сбор метрик подключается одной строкой `setup_metrics(app)` (модуль `app/metrics.py`): HTTP-middleware замеряет каждый запрос, кроме служебных путей (`/health`, `/metrics`, `/handlers`, `/docs` и т.п.).

| Метрика | Тип | Лейблы |
|---|---|---|
| `http_request_duration_seconds` | Histogram | `method`, `route`, `pod_id`, `datacenter` |
| `http_requests_total` | Counter | `method`, `route`, `status`, `pod_id`, `datacenter` |

Бакеты гистограммы: `0.5ms … 2.5s` (`0.0005, 0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5`).

### Лейблы

- method + route - определяет ручку которую мы проверяем; route - шаблон а не фактический адрес, чтобы не было отдельной строчки по каждому id
- все запросы на несуществующие адреса - route="unmatched", чтобы на каждый неизвестный адрес не было отдельной строчки
- status только у counter, потому что в длительности ответа нам не так важно какой статус в итоге отдал сервер, а как долго, на гистограмме они бы размножили ряды без добавления полезной информации
- pod и datacenter, для того чтобы определять нагрузку в отдельном поде или сервере, это нужно чтобы в дальнейшем на основе различий в показателей на серверах/подах можно было скорректировать распределение нагрузки


### Как метрики превращаются в панели

Для каждой ручки (`{sel}` = `method="…", route="…", datacenter=~"$datacenter", pod_id=~"$pod"`):

| Панель | PromQL |
|---|---|
| Latency p50/p95/p99 | `histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{sel}[$__rate_interval])))` |
| RPS | `sum(rate(http_requests_total{sel}[$__rate_interval]))` |
| Errors | `sum by (status) (rate(http_requests_total{sel, status=~"4..\|5.."}[$__rate_interval]))` |

`rate` всегда обёрнут в `sum`, а перцентили считаются по бакетам, просуммированным по выбранным подам и датацентрам, поэтому значения корректны при любом выборе в селекторах.

## Генератор дашборда

`generator/generate.py`:

1. `GET http://app1:8000/handlers` — список ручек, который приложение строит из своего роутера (`app.routes`), поэтому новая ручка в сервисе появится на дашборде после перезапуска стека, без редактирования кода.
2. Собирает JSON дашборда (чистая функция `build_dashboard`): на каждую ручку строка-заголовок и три панели; селекторы `datacenter` и `pod` (multi-value + All; список подов зависит от выбранного датацентра).
3. `POST /api/dashboards/db` с `overwrite: true` и фиксированным `uid` — повторный запуск перезаписывает дашборд, а не создаёт копию. Дашборд non-editable.

Datasource Prometheus создаётся provisioning'ом (`grafana/provisioning/datasources/datasource.yaml`) с фиксированным `uid: prometheus`, на который ссылаются панели.

Локальная отладка без Grafana — печать JSON дашборда:

```bash
cd generator
APP_URL=http://localhost:8001 python generate.py --dry-run
```

## Нагрузка

`load/load.js`, k6, executor `ramping-arrival-rate` (открытая модель: заданный RPS независимо от времени ответа):

- разгон от 1 до `TARGET_RPS=30` (суммарно на оба экземпляра) за `RAMP_DURATION=3m`, затем удержание до остановки стека;
- случайный экземпляр на каждый запрос; смесь: ~30% `POST`, ~45% `GET`, ~20% `PUT` по существующим id, ~5% `GET` по несуществующему id → `404`;
- id запоминаются отдельно для каждого экземпляра: у app1 и app2 разные in-memory хранилища;
- плюс ~3% `500` от `FAIL_RATE` на всех бизнес-ручках. Итого около 8% ошибок двух видов.

Параметры (`TARGET_RPS`, `RAMP_DURATION`, …) задаются через environment сервиса `load` в `docker-compose.yaml`.

## Секреты

Учётные данные администратора Grafana берутся из `.env` (он в `.gitignore`); в репозитории лежит только `.env.example`. В compose используется `${VAR:?…}`: без `.env` запуск падает с понятной ошибкой, а не поднимает Grafana с пустым паролем. Секреты передаются только сервисам `grafana` и `dashboard-generator`.

## Известные особенности

- Если на хосте заняты порты 9090 или 3000 (например, Prometheus/Grafana с другого проекта), поменяйте левую часть маппинга в `docker-compose.yaml`; внутренние адреса от этого не зависят.
- Некоторые VPN-клиенты перехватывают трафик к сетям Docker или DNS внутри контейнеров: сервисы недоступны с хоста или Grafana не находит `prometheus`. Помогает отключить VPN и выполнить `docker compose down && docker compose up`.
